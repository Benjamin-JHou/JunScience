# JunScience — 医学多模态能力(临床文本 / 医学影像 / 多模态)

## 背景

之前加的 ClinicalTrials.gov/openFDA/RxNorm 这批是"临床证据数据库",解决的是
"查药品/试验信息"。这次要加的是完全不同的另一件事:**医学 AI 方法学研究能力
——检索这个领域的论文、方法、基准,以及真正处理临床文本/影像数据的能力**。
两者都要做,分开设计,不要混在一起。

## 硬性原则(必须先定死,不是可选项)

**任何真实的(哪怕去标识化的)临床文本或医学影像数据,默认只能在本地
Python 沙盒里处理,不能被发送给用户配置的外部模型 API。**

原因:`GenericModelClient` 调用的是用户自己配置的第三方 endpoint(比如
Agnes AI),任何发过去的内容都会离开用户本机。查文献、查数据库这些是公开
数据,没问题;但临床文本/影像属于潜在敏感数据,不能默认走同样的路径。

具体要求:
- 如果 `AutonomousResearchEngine` 在处理流程中需要把临床文本/影像的内容
  片段发给 LLM 做推理(比如"帮我总结这段临床记录里的关键发现"),必须先
  弹出一个明确的用户确认(Desktop UI 对话框 / CLI 交互式确认),说明"这段
  内容将被发送到你配置的模型 API",不能默认静默发送。
- 优先设计成"本地处理产出结构化结果(比如提取的实体、影像特征),只把
  结构化结果的摘要发给 LLM 做进一步推理,而不是把原始文本/影像整个发过
  去"——这样能大幅减少真正敏感的原始内容被发送出去的情况。

## 任务 A:医学 AI 方法学研究能力(文献/基准检索层)

新增连接器,复用现有的限流退避 + CritiqueEngine 核查模式:

- **arXiv API** —— 医学影像 AI、多模态医学大模型这类论文大量发在 arXiv,
  PubMed 覆盖不到,必须补上。
- **medRxiv / bioRxiv API** —— 临床 AI 预印本,尤其 medRxiv 和"临床"方向
  高度相关。
- **Papers With Code API** —— 检索某个任务(比如"胸部 X 光分类"、"病理
  切片分割")的公开基准、SOTA 方法、代码仓库链接。
- **Hugging Face Hub API** —— 检索现成的医学影像/临床 NLP 模型和数据集
  (模型卡片、下载量、任务标签),用于"这个任务有哪些现成模型可用"这类
  研究问题。

这四个连接器的定位是"研究这个领域",不涉及用户真实数据,风险和现有的
PubMed/UniProt 连接器是一个量级,可以直接照现有模式做。

## 任务 B:实际处理临床文本/影像数据的能力

### B1. 临床文本 NLP(本地处理,Python 沙盒内)

在 Python 沙盒的科学计算环境里加入:
- **scispaCy / medspaCy** —— 生物医学/临床命名实体识别(疾病、药物、
  解剖部位等)、否定检测(negation detection,比如区分"患者无胸痛"和
  "患者有胸痛")、上下文断言(assertion status)。这些库相对轻量,能在
  本地 CPU 上跑,不需要 GPU。
- 明确不做:不要在这个阶段承诺集成 ClinicalBERT/GatorTron 这类大型
  临床语言模型的本地推理——这些模型体积大(GB 级)、通常需要 GPU,和
  "轻量级可下载桌面应用"这个产品定位冲突。如果之后真的需要用到这类
  模型的能力,应该走"调用外部推理 API"这条路径,并且同样要过前面提到
  的用户确认这道闸门。

### B2. 医学影像处理(本地处理,Python 沙盒内)

在 Python 沙盒里加入:
- **pydicom**(读取 DICOM 文件元数据与像素数据)
- **nibabel**(读取 NIfTI 格式,常见于 MRI/CT 研究数据)
- **SimpleITK / scikit-image**(基础图像处理、配准、分割)
- **pyradiomics**(从影像里提取放射组学特征——形状、纹理、强度统计量,
  这是目前"影像 + 机器学习"科研里最常见的一类可本地完成、不需要深度
  学习模型的分析路径)

明确不做(这次先不承诺):不在桌面应用安装包里内置任何预训练深度学习
影像模型的权重文件——同样是体积和分发成本的问题(参考之前 Codex 二进制
分发那次的讨论)。如果需要"用一个现成模型对影像做分类/分割"这类需求,
设计成可选的 Hugging Face Inference API 调用(需要用户自己的 HF token,
且同样要过用户确认这道闸门,因为影像数据会被发送出去)。

### B3. 多模态(文本+影像联合推理)

请先回答一个具体问题,不要假设:**`GenericModelClient` 现在发送给模型的
请求,能不能带图片(image content block)?** 如果现有实现只支持纯文本
消息,这是这次要补的最基础的一块——因为"多模态推理"这件事,大部分情况
下应该直接复用用户自己配置的模型本身的多模态能力(现在主流模型基本都能
接受图片输入),而不是 JunScience 自己再造一个独立的视觉模型。JunScience
要做的是把 B2 里提取出来的影像(或者影像的关键切片/可视化结果)正确地
放进发给模型的请求里,并且这一步同样要走前面说的用户确认。

## 验收标准

- **任务 A**:用一个具体问题测试,比如"胸部 X 光片肺炎分类目前公开的
  SOTA 方法有哪些,分别用了什么数据集",看 arXiv/Papers With Code/HF Hub
  这几个连接器是否真的被 `AutonomousResearchEngine` 调用并给出具体、
  可核查的论文/基准/模型名称,而不是模型凭训练记忆编出来的内容。
- **任务 B**:用一份**公开的、非真实患者的**示例数据测试,比如
  MTSamples 上的公开医学转录样本(临床文本)、TCIA 或其他公开影像库里
  的一份公开授权的示例 DICOM/NIfTI 文件(医学影像)。确认:
  - 处理过程全部发生在本地 Python 沙盒,能给出具体证据(比如网络流量
    日志显示处理阶段没有出站请求)
  - 只有在明确弹出用户确认之后,相关内容摘要才会被发送给外部模型 API
  - 不能用真实患者数据做这次测试,即使是你自己手头的也不行,用公开
    示例数据即可验证功能。

## 执行顺序

先做任务 A(风险低,复用现有模式,做起来快)。任务 B 先完成"用户确认
闸门"这个机制本身(这是安全设计,必须先有),再分别做 B1(临床文本)、
B2(医学影像)、B3(多模态,依赖前面回答的 GenericModelClient 图片支持
情况)。不要在没有用户确认闸门的情况下,先做出能处理真实数据的功能。
